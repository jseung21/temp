기존 ETL 시스템의 한계와 Modern Data Stack으로의 전환 필요성

🔴 기존 시스템 공통 문제점

  • 모놀리식 아키텍처로 인한 확장성 한계 — Extract/Transform/Load가 단일 프로세스에 결합
  • 장애 발생 시 전체 파이프라인 중단 (Single Point of Failure)
  • 배치 처리 위주로 실시간/준실시간 데이터 요구 대응 불가
  • 데이터 품질 검증이 후행적(reactive)이고 자동화 미흡
  • 파이프라인 변경 시 영향도 분석 및 배포 리스크 높음
  • 데이터 리니지(Lineage) 추적 어려움으로 거버넌스 약화

🟢 Modern ETL이 추구하는 방향

  • Microservices 기반: E, T, L 각 단계를 독립 배포·스케일링 가능하도록 분리
  • Batch + Streaming 하이브리드: 배치와 실시간 처리를 단일 아키텍처에서 지원
  • ELT 패러다임 전환: Raw 데이터를 먼저 적재하고, DW/Lakehouse의 연산 파워로 변환
  • Data Quality as Code: 자동화된 품질 검증 게이트를 파이프라인에 내장
  • Asset-First Orchestration: 태스크가 아닌 데이터 자산 중심의 파이프라인 관리
  • Data as a Product: 데이터를 발견 가능하고, SLA가 보장되는 프로덕트로 제공
반도체 데이터 특성 고려: 반도체 제조 데이터는 Variety(센서·설비·공정·계측 등 이종 데이터), Velocity(고빈도 시계열 센서 데이터), Volume(일 수 TB~PB 규모), Veracity(데이터 품질이 Yield 분석의 핵심)라는 4V 특성이 극대화됩니다. Databricks 등 Lakehouse 아키텍처가 반도체 데이터의 이러한 특성에 적합하며, Intel, AMD, NVIDIA, ASML 등이 이미 도입하고 있습니다.

🏗️ Option A: Lakehouse 중심 구성

반도체 데이터에 가장 적합한 구성

  • 수집: Airbyte(DB/SaaS) + Kafka(설비 센서) + Debezium(CDC)
  • 저장: Databricks / Delta Lake (Medallion Architecture)
  • 변환: dbt Core + Apache Spark (대용량 시계열 처리)
  • 오케스트레이션: Dagster (Asset-first, 데이터 리니지)
  • 품질: Great Expectations + dbt tests
  • 장점: 대용량 센서 데이터 처리에 최적, ET/OT/IT 데이터 통합, ML 워크로드 지원

🏗️ Option B: Cloud DW 중심 구성

SaaS 데이터 중심, 빠른 구축 시

  • 수집: Fivetran(Managed ELT) + Kafka(이벤트)
  • 저장: Snowflake / BigQuery
  • 변환: dbt Cloud (Managed)
  • 오케스트레이션: Airflow 3.0 (DAG Versioning, Event-driven)
  • 품질: dbt tests + Snowflake Data Quality
  • 장점: 운영 부담 최소화, 빠른 PoC, SaaS 데이터 통합에 강점

🔄 Medallion Architecture (Bronze → Silver → Gold)

Lakehouse 패턴의 핵심 — 데이터를 3개 계층으로 점진적으로 정제합니다.

계층 역할 데이터 특성 반도체 적용 예시
Bronze Raw 데이터 그대로 적재 비정제, 원본 보존, 감사 추적용 설비 센서 Raw Log, MES 이벤트
Silver 정제·표준화·조인 클렌징, 중복 제거, 스키마 정규화 공정별 통합 데이터, 계측 표준화
Gold 비즈니스 모델·집계 분석/리포팅 최적화, Pre-aggregated Yield 분석 마트, 설비 건강도 대시보드

오케스트레이션 선택 가이드: Data as a Product 개념을 추진 중이라면 Dagster가 가장 적합합니다. Asset-first 접근법이 데이터 프로덕트의 소유권·SLA·리니지 추적에 자연스럽게 연결되며, dbt 모델을 Asset으로 자동 매핑하여 end-to-end 가시성을 제공합니다. 벨기에 공공기관 사례에서는 Dagster 도입 후 파이프라인 배포 속도가 2배 향상되었습니다.

🔄 변환 (Transformation)

dbt (Data Build Tool)

  • SQL SELECT문으로 변환 로직 정의 — 분석가도 기여 가능
  • 모듈형 모델, 자동 테스트, 문서 생성
  • Git 기반 버전 관리 & CI/CD 연동
  • dbt Core (오픈소스) / dbt Cloud (매니지드) 선택
  • Dagster와 네이티브 통합 시 Asset 자동 매핑

Apache Spark

  • 대용량 분산 처리 엔진 (PB 규모)
  • Python/SQL/Scala 모두 지원
  • 배치 + 스트리밍 통합 처리 (Structured Streaming)
  • ML 파이프라인 통합 (MLflow)
  • 설비 센서 시계열 대용량 처리에 필수

단계별 구축 로드맵

PoC부터 전사 확대까지 4단계 접근

Phase 1 — Foundation & PoC

1~2개월

핵심 인프라 구축과 1~2개 파이프라인 PoC 수행. Lakehouse(Delta Lake/Iceberg) 환경 세팅, Airbyte로 주요 소스 연동 PoC, dbt 프로젝트 초기 구성 및 Medallion Architecture(Bronze/Silver/Gold) 레이어 설계. Dagster 로컬 환경 구성 및 기본 Asset 정의. 기존 ETL 대비 성능·안정성 벤치마크 수행.

Phase 2 — Core Pipeline 구축

2~4개월

핵심 데이터 도메인(예: 공정 데이터, 설비 데이터) 파이프라인 본격 구축. Kafka + Debezium CDC 도입으로 실시간 스트리밍 레이어 추가. dbt 모델링 표준화 및 Data Quality 게이트(Great Expectations) 적용. Dagster Asset 그래프 구성 및 모니터링/알림 체계 확립. CI/CD 파이프라인 구성(dbt + Dagster 배포 자동화).

Phase 3 — 확장 & 마이그레이션

3~6개월

기존 ETL 워크로드 단계적 마이그레이션. 추가 데이터 도메인 확장(계측, 품질, SCM 등). Data Catalog 연동 및 Data as a Product 체계 적용. 데이터 리니지 end-to-end 추적 완성. SLA 정의 및 데이터 프로덕트 계약 체계 구축.

Phase 4 — 최적화 & 자동화

6개월~

성능 최적화(파티셔닝, 인크리멘탈 처리, 캐싱 전략). ML 파이프라인 통합(Feature Store, Model Training). Self-service 데이터 접근 체계 고도화. 데이터 옵저버빌리티 대시보드 운영. 기존 ETL 시스템 완전 Decommission.

핵심 성공 요소: ① PoC 단계에서 기존 시스템 대비 명확한 성능·안정성 개선을 정량적으로 입증할 것 ② 변환 로직을 코드(dbt)로 전환하는 것이 가장 큰 문화적 변화 — 교육 투자 필요 ③ 기존 파이프라인을 한 번에 전환하지 말고, 도메인 단위로 점진적 마이그레이션 ④ Data Quality Gate를 파이프라인에 내장하여 장애를 사전에 차단
